# Plan — `rserver`: CLI para administrar redirects

> **Para agentes:** ejecutar paso a paso (§0 → §6). Cada paso sigue el ciclo del proyecto: `backend-engineer` → `[feat]`, `test-engineer` → `[test]`, `docs-engineer` → `[docs]`. Los checkboxes (`- [ ]`) registran el avance.

**Spec:** `docs/spec/2026-11-19_01_cli-rserver.md` (leerlo completo antes de cada paso; este plan argumenta desde él)
**Fecha:** 2026-11-19
**Rama:** `dev`
**Estado:** PENDIENTE

**Objetivo:** binario Rust `rserver` que administra redirects a través de la API v1 usando una API Key obtenida con `rserver login`.

**Arquitectura:** crate independiente en `cli/`. Tres capas: configuración local (`config`), cliente HTTP de la API v1 que mapea errores de la API a mensajes para el usuario (`api`), y comandos (`commands/*`) que solo orquestan y formatean la salida (`output`). Las operaciones con efectos externos (abrir navegador, leer stdin, hora actual, hostname) se inyectan para que la lógica de cada comando sea testeable sin red real ni terminal.

**Stack:** Rust (edición 2021, toolchain estable instalado), `cargo`. El spec deja la elección de crates al builder (ver "Lo que queda a criterio del builder" en el spec).

## Restricciones globales

- Binario: `rserver`. Crate en `cli/`, con `Cargo.toml` propio; no se toca el `package.json` salvo para el script `install:cli` (§5).
- **Nunca** escribir a Firestore ni modificar el servidor (`src/`). Todo pasa por `/api/v1`.
- **Nunca** persistir el JWT. **Nunca** imprimir el token `sk_1kg_...` después de guardarlo.
- Config: `${XDG_CONFIG_HOME:-~/.config}/rserver/config.toml`, permisos `600` (directorio `700`). Claves: `api_url` y la API Key (`token` + `id`).
- API Key creada por `login`: `name = "rserver@<hostname>"`, `scopes = ["read:redirects", "write:redirects"]`, `expiresAt` = ahora + 90 días (ISO 8601).
- `api_url` por defecto al instalar: `https://1kg.me`.
- Autenticación de comandos de redirects: `Authorization: Bearer <token>`.
- Salida: tabla por defecto; `--json` emite únicamente el `data` de la respuesta en stdout. Mensajes, prompts y advertencias van a **stderr**. Error → código de salida ≠ 0.
- `list`/`search`: columnas `id`, `path`, `url`. `view`: todos los campos.
- `list`: 20 por página por defecto. `--order` ∈ {`created`, `updated`, `path`}, con prefijo `-` opcional.
- Tests del crate con `cargo test` en `cli/`, sin red real (servidor HTTP mock local) y sin tocar el `$HOME` real (directorio temporal vía `XDG_CONFIG_HOME`).
- `npm test` del servidor no debe verse afectado.
- `cli/target/` va en `.gitignore`.

## Focos de revisión

Entradas o fallos que el spec implica, que ningún test obvio cubre y que más probablemente le pasen a una persona real. Cada uno tiene su test asignado en el paso dueño:

1. **`api_url` apunta a algo que no es la API v1** (servidor local apagado, o `https://1kg.me` mientras `main` no tenga API y responda HTML): mensaje claro que menciona la `api_url` configurada y sugiere `rserver set --api-url`; nunca un panic ni un error de parseo de JSON crudo. → §1
2. **Key expirada o revocada a mitad de uso** (401 con `API key expired` / `API key revoked`): mensaje que indica ejecutar `rserver login`, salida ≠ 0. Sin key configurada: el mismo consejo, sin hacer la petición. → §1
3. **Token pegado con ruido**: espacios o salto de línea al final, comillas, o el JSON completo del callback (`{"message":…,"data":{"token":…}}`) en lugar de solo el token. Se acepta y se extrae el JWT; si queda vacío, se pide de nuevo o se aborta con mensaje claro. → §2
4. **Referencias a un redirect que no existen o son ambiguas**: path inexistente → "no se encontró un redirect con path …"; id inexistente → el 404 de la API traducido; un path sin `/` inicial se trata como id (regla del spec), y el mensaje de "no encontrado" lo sugiere. → §1
5. **`delete` sin terminal interactiva** (stdin no es TTY, p. ej. en un pipe) y sin `--yes`: abortar con error en lugar de quedarse esperando; con `--json`, stdout contiene solo JSON válido incluso cuando hay advertencias. → §3

## §1 — Cliente de la API, `list` y `view`

**Archivos:** crear `cli/src/api.rs`, `cli/src/output.rs`, `cli/src/commands/list.rs`, `cli/src/commands/view.rs`, `cli/src/resolve.rs`.

**Interfaces:**
- Consume: `config::load()`.
- Produce:
  - `Redirect { id, path, url, owner, categories: Vec<String>, permission: Vec<String>, click_count: Option<u64>, created, updated }`, deserializado del JSON de la API (`clickCount` en camelCase; `categories`/`permission` vacíos si vienen ausentes).
  - `ApiClient::new(api_url, token: Option<String>)` con `list_redirects(offset: Option<u32>, limit: u32, order_by: Option<&str>) -> Result<Vec<Redirect>>`, `get_redirect(id) -> Result<Redirect>`, y métodos genéricos para `POST`/`PATCH`/`DELETE` que reutilizan §2 y §3.
  - `ApiError` con variantes que distinguen: sin key configurada, 401 (key expirada/revocada/inválida), 403, 404, 400 de validación (con el `message` de la API), servidor inalcanzable, respuesta que no es JSON de la API.
  - `fetch_all(client) -> Result<Vec<Redirect>>`: recorre páginas hasta recibir menos elementos que el tamaño de página.
  - `resolve_target(client, arg: &str) -> Result<Redirect>`: si `arg` empieza con `/`, busca coincidencia **exacta** de `path` en `fetch_all`; si no, `get_redirect(arg)`.

**backend-engineer:**
- [ ] `ApiClient` traduce cada `ApiError` a un mensaje en stderr. Para 401, "tu API Key expiró o fue revocada: ejecuta `rserver login`". Para inalcanzable o no-JSON, el mensaje incluye la `api_url` y sugiere `rserver set --api-url`. Sin key configurada, se falla antes de hacer la petición con el mismo consejo de `login`.
- [ ] `list [--page N] [--limit N] [--order <campo>]`. La API rechaza `offset=0` (mínimo 1), así que `offset = (page-1)*limit` y se omite cuando vale 0. `--page` y `--limit` deben ser ≥ 1. `--order` fuera de los valores permitidos se rechaza en el CLI.
- [ ] `view <id|path>` usa `resolve_target` y muestra todos los campos del `Redirect`. Las fechas se formatean de forma legible (a criterio del builder).
- [ ] `output`: tabla de `id`, `path`, `url` para listas; vista de detalle para un redirect; con `--json`, solo el `data` serializado en stdout.

**test-engineer** (servidor HTTP mock local; `XDG_CONFIG_HOME` temporal):
- [ ] `list` manda `Authorization: Bearer <token>` y `limit=20` sin `offset` por defecto; `--page 3 --limit 10` manda `offset=20&limit=10`; `--order -created` manda `orderBy=-created`; `--order foo` y `--page 0` fallan sin hacer petición.
- [ ] `list --json` produce en stdout un arreglo JSON parseable idéntico al `data` del mock; la tabla contiene solo id, path y url.
- [ ] `fetch_all` concatena páginas y se detiene en la primera página incompleta (mock con 2 páginas llenas + 1 parcial → 3 peticiones).
- [ ] `resolve_target("/fc/seminar")` devuelve el redirect con ese path exacto y no el de `/fc/seminar-2`. Un path inexistente da el error "no se encontró…". `resolve_target("abc123")` llama a `GET /redirects/abc123`.
- [ ] **Foco 1:** con el servidor apagado (puerto cerrado), y con una respuesta HTML 404, el comando sale con código ≠ 0 y el stderr contiene la `api_url` y `rserver set --api-url`.
- [ ] **Foco 2:** con un 401 `{"message":"API key expired"}` o sin key en la config, el stderr contiene `rserver login` y la salida es ≠ 0. Sin key, el mock no recibe ninguna petición.
- [ ] **Foco 4:** `view` con un id que da 404 muestra un mensaje legible. `view fc/seminar` (sin `/`) se trata como id.

**Commits:** `[feat] rserver API client, list and view commands` · `[test] cover rserver list, view, pagination and error mapping` · `[docs]`.

## §2 — `login` y `logout`

**Archivos:** crear `cli/src/commands/auth.rs`.

**Interfaces:**
- Consume: `Config`, `config::save`, `ApiClient` (sus métodos genéricos, aquí autenticando con el JWT en lugar de la key).
- Produce:
  - `extract_jwt(input: &str) -> Option<String>`: limpia espacios y comillas; si el texto es el JSON del callback, extrae `data.token`.
  - `login_with_jwt(client, jwt, hostname, now) -> Result<ApiKeyConfig>`: lista `GET /api/v1/users/me/api-keys`, revoca con `DELETE /:keyId` las keys **activas** cuyo `name` sea `rserver@<hostname>`, y crea la nueva con `POST` (name, scopes y `expiresAt` según las restricciones globales). Devuelve `{ id, token }` de la respuesta.
  - `logout_with_jwt(client, jwt, key_id) -> Result<()>`.
  - Un trait o función inyectable para "abrir URL en el navegador" y otro para "leer una línea de stdin", de modo que los tests sustituyan ambos.

**backend-engineer:**
- [ ] `login`: abre `{api_url}/api/v1/auth/google`. Si no se puede abrir, imprime la URL en stderr. Luego pide que se pegue el `token` del JSON, aplica `extract_jwt`, llama a `login_with_jwt` y guarda la key en la config. El JWT no se escribe nunca a disco ni se imprime. Al terminar, confirma en stderr con el `name` y la fecha de expiración, sin mostrar el token.
- [ ] `logout`: si no hay key guardada, error "no hay sesión". Si la hay, repite el flujo navegador → pegar JWT, llama a `DELETE /api/v1/users/me/api-keys/{id}` y solo entonces borra `api_key` de la config, conservando `api_url`. Si la API responde 404 (la key ya no existe), se trata como éxito y se borra localmente. Cualquier otro error deja la config intacta y se reporta (decisión del spec).
- [ ] Si el JWT pegado es rechazado (401), el mensaje dice que el token es inválido o expiró y que hay que repetir el login en el navegador.

**test-engineer:**
- [ ] **Foco 3:** `extract_jwt` acepta `"  eyJ…\n"`, `"\"eyJ…\""`, el JSON completo del callback (devuelve `data.token`) y devuelve `None` para entrada vacía o JSON sin `data.token`.
- [ ] `login_with_jwt` con el mock: el `POST` lleva `Authorization: Bearer <jwt>`, `name = "rserver@host-test"`, los dos scopes exactos y `expiresAt` = `now` + 90 días. Revoca solo las keys activas con ese mismo `name`: no toca `rserver@otra-maquina` ni las inactivas.
- [ ] El flujo completo de `login`, con navegador y stdin inyectados, deja en la config el `id` y el `token` devueltos por el mock. El archivo de config no contiene el JWT.
- [ ] `logout`: un 200 borra la key y conserva `api_url`; un 404 también la borra; un 500 deja la config intacta y sale con código ≠ 0. Sin key guardada, falla sin abrir el navegador.
- [ ] Un JWT rechazado con 401 da el mensaje de token inválido y no modifica la config.

**Commits:** `[feat] rserver login/logout via Google OAuth JWT and API key lifecycle` · `[test] cover rserver login/logout and pasted token parsing` · `[docs]`.

## §3 — `create`, `edit` y `delete`

**Archivos:** crear `cli/src/commands/create.rs`, `cli/src/commands/edit.rs`, `cli/src/commands/delete.rs`.

**Interfaces:**
- Consume: `ApiClient`, `resolve_target`, `output`.
- Produce: nada que usen pasos posteriores.

**backend-engineer:**
- [ ] `create <path> <url> [--group <slug>] [--category <c>]... [--perm <scope:group>]...` → `POST /api/v1/redirects` con `path`, `url` y, solo si se pasan, `group`, `categories` y `permission`. El CLI **no** duplica las validaciones de Joi: los errores 400 de la API se muestran con su `message`. Muestra el redirect creado (detalle, o `data` con `--json`).
- [ ] `edit <id|path> [--url <u>] [--add-category <c>]... [--remove-category <c>]...` → resuelve el redirect, calcula `categories` final (actual + altas sin duplicar − bajas, preservando el orden existente) y manda un único `PATCH` con solo los campos que cambian. Sin ninguna bandera, error de uso. Quitar una categoría que no existe no es error.
- [ ] `delete <id|path> [--yes]` → resuelve el redirect y, sin `--yes`, pide confirmación en stderr mostrando path y url (`[y/N]`, default no). Si stdin no es TTY y no hay `--yes`, aborta con error. Al confirmar, `DELETE /api/v1/redirects/:id`.

**test-engineer:**
- [ ] `create` con `--group fc --category a --category b --perm read:fc` manda exactamente esos campos. Sin banderas opcionales, el body solo lleva `path` y `url`. Un 400 del mock (`"path" already taken`, etc.) llega a stderr con su mensaje y la salida es ≠ 0.
- [ ] `edit /fc/x --add-category b --remove-category a` sobre `categories: ["a","c"]` manda `{"categories":["c","b"]}`. `--add-category c` (ya presente) no duplica. `--url` junto con categorías va en un solo `PATCH`. Sin banderas, falla sin hacer petición.
- [ ] `delete --yes` llama a `DELETE` con el id resuelto. Con confirmación inyectada `n` no llama a `DELETE`; con `y` sí.
- [ ] **Foco 5:** `delete` sin `--yes` y con stdin no-TTY sale con código ≠ 0 sin llamar a `DELETE`. `create --json` y `delete --yes --json` producen en stdout un JSON parseable y nada más.

**Commits:** `[feat] rserver create, edit and delete commands` · `[test] cover rserver create, edit and delete` · `[docs]`.

## §4 — `search`

**Archivos:** crear `cli/src/commands/search.rs`.

**Interfaces:**
- Consume: `fetch_all`, `output`.
- Produce: `filter_redirects(items, path: Option<&str>, url: Option<&str>, category: Option<&str>) -> Vec<Redirect>` (función pura).

**backend-engineer:**
- [ ] `search [--path <txt>] [--url <txt>] [--category <c>]`: se requiere al menos un filtro. `--path` y `--url` buscan un fragmento sin distinguir mayúsculas; `--category` busca coincidencia exacta con alguna categoría. Varios filtros se combinan con AND (reglas del spec). La salida es la misma tabla que `list`, o un arreglo JSON con `--json`. Sin resultados: tabla vacía con aviso en stderr, o `[]` con `--json`, y código de salida 0.

**test-engineer:**
- [ ] `filter_redirects`: `--url DRIVE.google` encuentra `https://drive.google.com/x`; `--path semi` encuentra `/fc/seminar`; `--category Docs` **no** encuentra `docs` (exacta); `--path fc --category x` exige ambas condiciones.
- [ ] Sin filtros, error de uso. Sin resultados, salida 0 y `--json` imprime `[]`.
- [ ] `search` recorre todas las páginas del mock (reutiliza `fetch_all`).

## §5 — `npm run install:cli` y bash completion

**Archivos:** crear `scripts/install-cli.sh`; modificar `package.json` (script `"install:cli": "bash scripts/install-cli.sh"`); agregar el subcomando de completion en `cli/src/main.rs`.

**Interfaces:**
- Produce: subcomando `rserver completions bash`, que imprime el script de completion en stdout (oculto en `--help` o visible, a criterio del builder).

**backend-engineer:**
- [ ] `install-cli.sh`, en orden y abortando al primer error (`set -euo pipefail`):
  1. Verificar que `cargo` existe; si no, mensaje con instrucciones.
  2. `cargo build --release` en `cli/`.
  3. Copiar el binario a `~/.local/bin/rserver`, creando el directorio si falta. Advertir si `~/.local/bin` no está en `PATH`.
  4. Si el archivo de config **no** existe, ejecutar `rserver set --api-url https://1kg.me`. Si existe, no tocarlo.
  5. Escribir `rserver completions bash` en `${XDG_DATA_HOME:-~/.local/share}/bash-completion/completions/rserver`.
  6. Imprimir los siguientes pasos: `rserver set --api-url …` si aplica, y `rserver login`.
- [ ] Debe poder ejecutarse varias veces sin efectos indeseados: recompila, reemplaza el binario y el completion, y conserva la config.

**test-engineer:**
- [ ] Test de Rust: `rserver completions bash` sale con código 0 y su salida contiene los subcomandos `list`, `view`, `create`, `edit`, `delete`, `search`, `login`, `logout` y `set`.
- [ ] Verificación manual documentada en el commit, con `HOME` y `XDG_*` apuntando a un directorio temporal: la primera ejecución crea el binario, la config (con `https://1kg.me` y modo `600`) y el completion. La segunda ejecución conserva una config modificada a mano.
