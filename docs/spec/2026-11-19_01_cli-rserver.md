# Spec — `rserver`: CLI para administrar redirects

**Fecha:** 2026-11-19
**Rama:** `dev`
**Estado:** BORRADOR — pendiente de aprobación

---

## Contexto y motivación

Hoy no existe front ni colección de Postman para la API v1. La última vez que se creó un redirect, se insertó el documento **a mano en la consola de Firestore**. Eso salta todas las validaciones de la API: el formato del path, la unicidad, el namespace por grupo, el formato de `permission` y el `owner` derivado del usuario autenticado.

No se planea un front pronto. La API se integrará en otros servicios y cada grupo hará su propia integración. Por ahora el dueño del proyecto es el único que crea redirects.

`rserver` es un CLI para que el administrador gestione redirects **a través de la API**, de modo que toda escritura pase por las mismas validaciones y permisos que cualquier integración. Así se mantiene la integridad de los datos.

## Objetivos

- Crear, listar (paginado), ver en detalle, buscar, editar (url y categorías) y borrar redirects desde la terminal.
- Autenticación con API Key, obtenida una sola vez por máquina mediante `rserver login`, que pasa por Google OAuth.
- Binario nativo, optimizado y con instalación local de un solo comando.
- Salida legible para humanos (tabla) y `--json` para usar en pipes.
- Bash completion.

## No-objetivos

- Administrar usuarios, grupos o API Keys distintas a la del propio CLI.
- Cambios al servidor. El CLI usa la API v1 tal como existe hoy en `dev`.
- Búsqueda del lado del servidor (ver "Búsqueda").
- Distribución a otros usuarios (crates.io, releases binarias, Homebrew). Instalación solo local.
- Soporte para shells distintos de bash.

## Anti-objetivos

- **El CLI nunca escribe directo a Firestore.** Si algo no se puede hacer vía API, no se hace desde el CLI.
- **El CLI nunca persiste el JWT.** El JWT solo existe en memoria durante `rserver login`.
- El token de la API Key nunca se imprime en la salida después de guardarse.

## Decisiones tomadas con el dueño del producto

### Lenguaje y ubicación

- **Rust.** El objetivo es un binario nativo y optimizado.
- Vive en este repo, en `cli/`, como crate independiente (`cli/Cargo.toml`). El binario se llama `rserver`.
- No tiene relación de build con el servidor Node más allá del script npm de instalación.

### Instalación — `npm run install:cli`

Un script npm `install:cli` en el `package.json` raíz que, en orden:

1. Compila con `cargo build --release` dentro de `cli/`.
2. Copia el binario a `~/.local/bin/rserver`.
3. Crea el archivo de configuración si no existe (ver "Configuración"). Si ya existe, no lo sobreescribe.
4. Instala el bash completion generado por el propio binario en `~/.local/share/bash-completion/completions/rserver`. Es el directorio de usuario estándar que `bash-completion` 2.x carga bajo demanda (`$XDG_DATA_HOME/bash-completion/completions`). No requiere `sudo` ni tocar `~/.bashrc`.

Una vez instalado, el CLI se invoca directamente como `rserver ...`, **no** con `npm run`. No hay script `npm run cli`.

### Autenticación — `rserver login`

Flujo acordado (agreed solution):

1. `rserver login` abre el navegador en `{api-url}/api/v1/auth/google`.
2. Al terminar el flujo de Google, el navegador muestra el JSON de respuesta del callback (`{ message, data: { token, user } }`). El servidor no cambia.
3. El CLI pide en la terminal que el usuario **copie y pegue el `token`** (JWT).
4. Con ese JWT, el CLI llama a `POST /api/v1/users/me/api-keys` con:
   - `name`: identifica al CLI y a la máquina, p. ej. `rserver@<hostname>`.
   - `scopes`: `["read:redirects", "write:redirects"]`.
   - `expiresAt`: 90 días a partir de la creación.
5. Guarda el token `sk_1kg_...` devuelto en el archivo de configuración y descarta el JWT.

Desde ese momento, todos los comandos de redirects se autentican con `Authorization: Bearer sk_1kg_...`.

Si `rserver login` se ejecuta de nuevo en la misma máquina, el CLI usa el JWT de esa sesión para listar las keys del usuario (`GET /me/api-keys`) y revocar (`DELETE /me/api-keys/:keyId`) las keys activas con el mismo `name` antes de crear la nueva. Así no se acumulan keys hacia el límite de 10 activas.

Si no se puede abrir el navegador, el CLI imprime la URL para abrirla manualmente.

**Expiración.** La key vence a los 90 días. Cuando la API responde 401 por key expirada o revocada, el CLI muestra un mensaje que indica ejecutar `rserver login`.

### Cierre de sesión — `rserver logout`

Decidido con el dueño del producto: **revocar en el servidor**. Una API Key no puede revocarse a sí misma, porque `DELETE /me/api-keys/:keyId` está detrás de `requireJwt`. Por eso `logout` repite los pasos 1–3 de `login` (abre el navegador y pide pegar el JWT), llama a `DELETE /api/v1/users/me/api-keys/:keyId` con el `id` guardado en la config y después elimina la API Key del archivo local. Si la revocación falla, la config local no se borra y el error se reporta.

### Configuración

- Archivo: `~/.config/rserver/config.toml`, con permisos `600`.
- Contenido: `api_url` y la API Key (token y su `id`, necesario para revocarla).
- `rserver set --api-url <url>` modifica la URL del servidor en el archivo. Es la única forma prevista de cambiarla; no hay flags por comando ni variables de entorno.
- El archivo creado por `install:cli` trae `api_url = "https://1kg.me"` y no trae API Key. Mientras la API de `dev` no esté en producción, se apunta a local con `rserver set --api-url http://localhost:3000`. *(Decisión del builder en la revisión.)*

### Comandos

| Comando | Descripción | Endpoint |
|---|---|---|
| `rserver login` | Flujo descrito arriba | `GET /auth/google` (navegador), `GET/POST/DELETE /users/me/api-keys` |
| `rserver logout` | Revoca la API Key en el servidor y la borra de la config | `GET /auth/google` (navegador), `DELETE /users/me/api-keys/:keyId` |
| `rserver set --api-url <url>` | Cambia la URL del servidor | — |
| `rserver create <path> <url> [--group <slug>] [--category <c>]... [--perm <scope:group>]...` | Crea un redirect | `POST /redirects` |
| `rserver list [--page N] [--limit N] [--order <campo>]` | Lista paginada | `GET /redirects?offset&limit&orderBy` |
| `rserver view <id\|path>` | Detalle completo de un redirect | `GET /redirects/:id` |
| `rserver search [--path <txt>] [--url <txt>] [--category <c>]` | Búsqueda filtrada en el CLI | `GET /redirects` (todas las páginas) |
| `rserver edit <id\|path> --url <nueva>` | Cambia el destino | `PATCH /redirects/:id` |
| `rserver edit <id\|path> [--add-category <c>]... [--remove-category <c>]...` | Agrega o quita categorías | `PATCH /redirects/:id` |
| `rserver delete <id\|path> [--yes]` | Borra con confirmación interactiva, salvo `--yes` | `DELETE /redirects/:id` |

Detalles:

- **`create`**: el `path` se pasa como lo espera la API: sin `/` inicial y sin el prefijo de grupo cuando se usa `--group`. La API construye `/{group}/{path}`. Como admin, sin `--group`, el path queda en la raíz.
- **`edit` de categorías**: la API reemplaza el arreglo completo en `PATCH`. El CLI lee el redirect, aplica las altas y bajas y manda el arreglo resultante.
- **`<id|path>`**: `view`, `edit` y `delete` aceptan el id de Firestore o el path completo (`/fc/seminar`). Un argumento que empieza con `/` se trata como path. La API no tiene búsqueda por path, así que el CLI lo resuelve recorriendo el listado.
- **`list`**: página de 20 resultados por defecto. `--page N` se traduce a `offset`/`limit`. `--order` acepta `created`, `updated` y `path`, con prefijo `-` para orden descendente. *(Decisión del builder en la revisión.)*
- **`edit`**: `--url` y las banderas de categorías se pueden combinar en una sola invocación y se envían en un solo `PATCH`. Sin ninguna bandera es un error. *(Decisión del builder en la revisión.)*
- **`delete`** es borrado definitivo en el servidor (los redirects no tienen soft-delete).

### Búsqueda — en el CLI

`GET /redirects` solo acepta `orderBy`, `offset` y `limit`. Se acordó **filtrar en el CLI por ahora**: `search` recorre todas las páginas y filtra localmente.

- Coincidencia por fragmento, sin distinguir mayúsculas.
- Si se pasan varios filtros, deben cumplirse todos (AND).
- `--category` busca coincidencia exacta con alguna de las categorías del redirect.

Trade-off aceptado: cada búsqueda lee todos los redirects visibles para el usuario, lo que implica lecturas de Firestore proporcionales al total. Con el volumen actual (un solo usuario y pocos redirects) es despreciable. Si el volumen crece, la búsqueda se puede mover a la API sin cambiar la interfaz del comando.

### Salida

- Por defecto, tabla legible para humanos.
- `list` y `search` muestran solo las columnas **id, path y url**.
- `view` muestra todos los campos del redirect: id, path, url, owner, categories, permission, clickCount, created y updated.
- `--json` en cualquier comando de lectura o escritura emite el `data` de la respuesta de la API como JSON, sin decoración, para encadenar con `jq`.
- Los errores van a stderr con el `message` de la API y un código de salida distinto de cero.

## Supuestos verificados

- Todos los redirects existentes en Firestore, incluidos los creados a mano, tienen `created`, `updated` y `owner` (confirmado por el dueño del producto). No hace falta migración previa.

## Lo que queda a criterio del builder

- Crates (parser de argumentos, cliente HTTP, TLS, tablas, TOML, apertura del navegador, generación de completion).
- Estructura interna del crate y del manejo de errores.
- Nombre exacto de las columnas y formato de fechas en la tabla.
- Tamaño de página interno que usa `search` para recorrer el listado.
- Cómo implementar el script `install:cli` (inline en `package.json` o como script en `scripts/`).
- Estrategia de tests del crate.
